## SoC Integration

Instantiate the `USBHostController` in your LiteX SoC builder script
and connect it to the Wishbone bus and interrupt controller:

```python
from liteusb.gateware.usb.usb2.host import USBHostController

class MySoC(SoCCore):
    def __init__(self, platform, **kwargs):
        # ...

        # Request the ULPI pads from the platform
        ulpi_pads = platform.request("ulpi")

        # Create the EHCI host controller
        # Uses ULPI PHY (TUSB1210, USB3300, etc.) at 60 MHz
        self.submodules.usb_host = USBHostController(
            bus=ulpi_pads,
            handle_clocking=True,
            num_ports=1,
            domain_clock=60e6,
        )

        # Map into the Wishbone bus at a fixed address
        # The EHCI operational registers start at this base address
        self.bus.add_slave("usb_ehci", self.usb_host.bus,
            region=SoCRegion(origin=0xe0000000, size=0x1000, cached=False))

        # Route the interrupt (use an available IRQ line)
        self.comb += self.cpu.interrupt[17].eq(self.usb_host.interrupt)
```

### GatewarePHY (Full-Speed Only)

For FPGA I/O-only operation without an external ULPI PHY, use the built-in
GatewarePHY. This limits operation to full-speed (12 Mbps):

```python
usb_pads = platform.request("usb_host")  # dp/dm raw I/O pads
self.submodules.usb_host = USBHostController(
    bus=usb_pads,
    handle_clocking=True,
    num_ports=1,
    domain_clock=12e6,
)
```

> **Note:** GatewarePHY requires a 48 MHz `usb_io` clock domain and a 12 MHz
> `usb` clock domain. Both must be phase-related. See the GatewarePHY
> documentation for platform-specific constraints.

## Memory Map

The EHCI operational registers are mapped at the Wishbone base address.
The capability registers precede the operational registers by `CAPLENGTH`
bytes (0x20 in this implementation).

| Offset      | Register          | Description                    |
|-------------|-------------------|--------------------------------|
| 0x00        | CAPLENGTH         | Capability registers length    |
| 0x02        | HCIVERSION        | EHCI revision (1.0 = 0x0100)   |
| 0x04        | HCSPARAMS         | Structural parameters          |
| 0x08        | HCCPARAMS         | Capability parameters          |
| 0x20        | USBCMD            | USB command                    |
| 0x24        | USBSTS            | USB status                     |
| 0x28        | USBINTR           | USB interrupt enable           |
| 0x2C        | FRINDEX           | Frame index                    |
| 0x30        | CTRLDSSEGMENT     | 64-bit addressing segment      |
| 0x34        | PERIODICLISTBASE  | Periodic frame list base addr  |
| 0x38        | ASYNCLISTADDR     | Async list address             |
| 0x60        | CONFIGFLAG        | Configure flag                 |
| 0x64        | PORTSC1           | Port status & control (port 1) |

Operational register offsets follow the EHCI spec (§2.2) relative to the
operational base: USBCMD+0x00 … ASYNCLISTADDR+0x18, CONFIGFLAG+0x40,
PORTSC+0x44. With CAPLENGTH=0x20 this yields the absolute offsets above.

The driver accesses the operational registers at `base + 0x20` and uses
the frame list and async schedule structures in system RAM.

### Data Structures in RAM

The EHCI driver allocates the following in coherent DMA memory:

- **Periodic Frame List**: 4 KB, 4K-aligned. 1024 × 4-byte entries.
- **Queue Heads (QH)**: 48 bytes each, 32-byte aligned.
- **Transfer Descriptors (qTD)**: 32 bytes each, 32-byte aligned.
- **Isochronous TDs (iTD)**: 64 bytes each, 32-byte aligned.

For RISC-V systems with an MMU, the driver uses `dma_alloc_coherent()`
to allocate these structures.

## Device Tree

Add an EHCI node to the device tree generated by `litex_json2dts_linux`:

### ULPI-based Controller

```dts
usb@e0000000 {
    compatible = "generic-ehci";
    reg = <0xe0000000 0x1000>;
    interrupt-parent = <&intc0>;
    interrupts = <17>;
    clocks = <&sys_clk>;
    big-endian;
    status = "okay";
};
```

### Explanation of Properties

| Property           | Value              | Notes                                                              |
|--------------------|--------------------|--------------------------------------------------------------------|
| `compatible`       | `"generic-ehci"`   | Matches Linux's `ehci-platform.c` driver                           |
| `reg`              | `<base size>`      | Wishbone base address and region size (4 KB typical)               |
| `interrupt-parent` | `<&intc0>`         | LiteX interrupt controller; use what `generate_dts_intc()` returns |
| `interrupts`       | `<17>`             | Interrupt line number; must match the `.eq(self.cpu.interrupt[17])` connection |
| `clocks`           | `<&sys_clk>`       | Reference to system clock; EHCI uses this for USB frame timing     |
| `big-endian`       | (none or present)  | Add `big-endian;` if the CPU is big-endian (EHCI registers are LE by default) |
| `status`           | `"okay"`           | Enable the controller                                              |

### RISC-V (LiteX VexRiscv) Full Example

```dts
/dts-v1/;

/ {
    compatible = "litex,vexriscv";
    model = "LiteX SoC with EHCI USB Host";

    cpus {
        cpu@0 {
            device_type = "cpu";
            compatible = "riscv";
        };
    };

    memory@40000000 {
        device_type = "memory";
        reg = <0x40000000 0x10000000>;
    };

    intc0: interrupt-controller@f0000000 {
        compatible = "litex,interrupt-controller";
        interrupt-controller;
        #interrupt-cells = <1>;
        reg = <0xf0000000 0x1000>;
    };

    soc {
        #address-cells = <1>;
        #size-cells = <1>;
        compatible = "simple-bus";
        ranges;

        usb@e0000000 {
            compatible = "generic-ehci";
            reg = <0xe0000000 0x1000>;
            interrupt-parent = <&intc0>;
            interrupts = <17>;
            clocks = <&sys_clk>;
            status = "okay";
            has-transaction-translator;
        };
    };
};
```

> The `has-transaction-translator` property informs the driver that this EHCI
> controller can directly handle full-speed and low-speed devices without a
> companion OHCI/UHCI controller. This matches our Integrated TT
> implementation.

## Clocks and PHY

### ULPI Clock Architecture (60 MHz)

```
FPGA PLL → 60 MHz → USB PLL → cd_usb (60 MHz) → ULPI CLK (to PHY)
                                         ↓
                                   usb clock domain (60 MHz gateware)
```

The ULPI PHY (TUSB1210, USB3300) generates a 60 MHz `CLOCK` output once it
receives `REFCLK`. This clock output drives the USB gateware domain.

**Important:** The `usb` clock domain reset **must NOT** be gated on the PLL
lock signal. The PHY only drives `CLOCK` after receiving `REFCLK`, creating a
circular dependency if the reset depends on the clock.

### GatewarePHY Clock Architecture (12/48 MHz)

```
FPGA PLL → 48 MHz → usb_io domain (clock recovery, sampling)
        → 12 MHz → usb domain (UTMI packet processing)
```

Both clocks must be phase-related (the 12 MHz clock should be divided down
from the 48 MHz clock).

### Clock Domain Constraints

Add these timing constraints for the ULPI interface:

```sdc
# ULPI I/O timing (60 MHz)
set_output_delay -clock cd_usb -max 6.0 [get_ports {ulpi_data[*] ulpi_stp}]
set_output_delay -clock cd_usb -min 2.0 [get_ports {ulpi_data[*] ulpi_stp}]
set_input_delay  -clock cd_usb -max 6.0 [get_ports {ulpi_data[*] ulpi_dir ulpi_nxt}]
set_input_delay  -clock cd_usb -min 2.0 [get_ports {ulpi_data[*] ulpi_dir ulpi_nxt}]

# Cross-domain false paths (sys ↔ usb)
set_false_path -from [get_clocks sys_clk] -to [get_clocks cd_usb]
set_false_path -from [get_clocks cd_usb] -to [get_clocks sys_clk]
```

## Kernel Configuration

Enable the following kernel options. Use `make menuconfig` or set them in
your kernel `.config`:

```
CONFIG_USB_SUPPORT=y
CONFIG_USB=y
CONFIG_USB_EHCI_HCD=y
CONFIG_USB_EHCI_HCD_PLATFORM=y
CONFIG_USB_EHCI_ROOT_HUB_TT=y
```

| Option                           | Purpose                                                             |
|----------------------------------|---------------------------------------------------------------------|
| `CONFIG_USB_EHCI_HCD`            | Core EHCI host controller driver                                    |
| `CONFIG_USB_EHCI_HCD_PLATFORM`   | Platform-device binding (probes from device tree, no PCI scan)      |
| `CONFIG_USB_EHCI_ROOT_HUB_TT`    | Integrated Transaction Translator support for FS/LS on root hub     |

### Optional: USB Device Drivers

Typical device drivers to enable alongside EHCI:

```
CONFIG_USB_STORAGE=y          # USB mass storage (flash drives)
CONFIG_USB_HID=y              # Keyboards, mice
CONFIG_USB_SERIAL=y           # USB-serial adapters (FTDI, CP210x, CDC-ACM)
CONFIG_USB_ETH=y              # USB Ethernet adapters
CONFIG_USB_UAS=y              # USB Attached SCSI (faster than BOT)
```

### Buildroot Integration

If using Buildroot, add these to your `defconfig`:

```
BR2_LINUX_KERNEL_USE_DEFCONFIG=y
# or
BR2_LINUX_KERNEL_DEFCONFIG="litex_vexriscv"
```

Then enable USB support in the kernel config fragment:

```
CONFIG_USB=y
CONFIG_USB_EHCI_HCD=y
CONFIG_USB_EHCI_HCD_PLATFORM=y
CONFIG_USB_EHCI_ROOT_HUB_TT=y
```

## Loading the Driver

### Built-in (recommended for LiteX)

With the options compiled into the kernel, the driver probes automatically
at boot when the device tree node is present. No manual loading needed.

Expected boot messages:

```
ehci-platform e0000000.usb: EHCI Host Controller
ehci-platform e0000000.usb: new USB bus registered, assigned bus number 1
ehci-platform e0000000.usb: irq 17, io mem 0xe0000000
ehci-platform e0000000.usb: USB 2.0 started, EHCI 1.00
hub 1-0:1.0: USB hub found
hub 1-0:1.0: 1 port detected
```

### Module (for testing)

If built as a module, load with:

```sh
modprobe ehci-hcd
modprobe ehci-platform
```

## Verification

### Check kernel messages

```sh
dmesg | grep -i ehci
dmesg | grep -i usb
```

Expected output includes:
- `EHCI Host Controller` — driver probed successfully
- `USB 2.0 started, EHCI 1.00` — controller initialized
- `1 port detected` — root hub port(s) enumerated

### Check USB devices

```sh
lsusb                    # List all USB devices
cat /proc/bus/usb/devices  # Detailed device tree
ls /sys/bus/usb/devices/   # sysfs view
```

### Test with a USB flash drive

```sh
# Insert a USB flash drive, then:
dmesg | tail -20
# Should show:
#   usb 1-1: new high-speed USB device number 2 using ehci-platform
#   usb-storage 1-1:1.0: USB Mass Storage device detected
#   scsi host0: usb-storage 1-1:1.0

lsblk                    # Should show the USB drive (e.g., /dev/sda)
mount /dev/sda1 /mnt     # Mount and verify
```

### Test interrupt delivery

```sh
cat /proc/interrupts | grep ehci
# Should show a non-zero interrupt count for the EHCI controller
```

### Full-speed device test

If using the integrated TT, connect a full-speed device (USB 1.1 keyboard,
mouse, or serial adapter) directly to the root port:

```sh
dmesg | grep "full-speed"
# Should show the device enumerated at full-speed via the integrated TT
```

## Debugging

### Common Issues

**"No EHCI controller found" at boot**
- Verify the device tree node is present and `status = "okay"`
- Check that the Wishbone address in DTS matches the SoC memory map
- Verify the kernel config includes `CONFIG_USB_EHCI_HCD_PLATFORM`

**Controller initializes but no devices detected**
- Check the PHY clock: verify 60 MHz present on ULPI CLK
- Check the ULPI I/O pin mapping in the platform file
- Verify the USB PLL is locked and running
- Probe with a known-good device (powered hub + flash drive)

**Interrupts not firing**
- Verify `cat /proc/interrupts` shows non-zero count for the EHCI IRQ
- Check interrupt routing in the device tree (`interrupts = <17>;`)
- Verify the interrupt line matches the SoC connection
- Try polling mode as a diagnostic: add `noints` option or remove `interrupts` from DTS

**ULPI I/O timing failures**
- Add the timing constraints from the Clocks section
- Register TX outputs: set `register_tx_outputs=True` in `USBHostController()`
- Check I/O standard: ULPI uses 3.3V LVCMOS

**Full-speed devices not working**
- Verify `CONFIG_USB_EHCI_ROOT_HUB_TT=y` is set
- Check that `has-transaction-translator` is in the device tree
- The integrated TT switches the PHY between HS and FS modes; ensure the
  ULPI PHY supports this (most do, including TUSB1210 and USB3300)

## Performance Notes

### Throughput

No throughput numbers are quoted: the DMA-backed schedule engine
(QH/qTD traversal) is not yet implemented, so sustained bulk throughput
does not exist yet. See the "Known limitations" section in the review
notes before integrating.

### Frame Timing

The SOF counter is synchronized to the 60 MHz USB clock. The 125 µs
microframe period (HS) or 1 ms frame period (FS/LS) is derived from
the PLL output. Frame accuracy depends on the FPGA PLL precision.

### Low-Speed Support

Low-speed (1.5 Mbps) devices require the Transaction Translator to send
a PRE PID preamble before each token. This adds ~60 µs overhead per
transaction at full-speed bus rates.
